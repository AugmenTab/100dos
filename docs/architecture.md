# Architecture Decisions

Decisions recorded here were made during initial skeleton development. The goal is to prevent future confusion and preserve context that would otherwise exist only in chat history.

---

## System identity

**System ID:** `100dos`
**System title:** `100DOS`

The ID is lowercase and hyphenated to satisfy Foundry's module naming requirements. The title uses the canonical stylization of the game name.

---

## Foundry version target

The system targets the latest stable Foundry release at the time of implementation. There is no floor version pinning and no legacy compatibility shim. If a Foundry release introduces a breaking API change, the system updates rather than maintaining backwards compatibility.

---

## Build tool: Vite

Vite bundles TypeScript source into a single ES module (`100dos.mjs`) and copies static assets (templates, lang files, styles, the manifest) to `dist/`. The `scripts/build` and `scripts/watch` shell scripts invoke it inside the dev container.

Vite was chosen for its fast rebuild cycle and minimal configuration overhead relative to alternatives like Webpack or Rollup directly.

---

## TypeScript

All source code is TypeScript. The compiler is used for type checking only (`tsc --noEmit`) — Vite handles the actual transpilation. Foundry's own types are ambient; they do not ship as a package and must be declared locally as needed.

TypeScript was chosen to catch structural errors early, particularly around Foundry's document and sheet APIs, which are large and have subtle contracts.

---

## Development environment: Docker

The development Foundry instance runs in Docker via `docker-compose.yml`. Developers run `scripts/up` to start it and access Foundry in a browser at the configured port. npm and Node commands must be run inside the container, not on the host.

Docker was chosen to avoid requiring contributors to manage a local Foundry installation and to ensure a consistent runtime across machines.

---

## Actor types

The system defines three actor types: `pc`, `npc`, and `vehicle`. No catch-all or generic actor type exists — everything maps to one of these three.

Two additional actor types are planned for the future but not yet designed:

- **`companion`**: A persistent follower NPC linked to a specific PC (e.g., a Ghost, a War Dog). The linking mechanism and resource-sharing behavior are not yet defined.
- **`group`**: Represents a party or collective entity. Intended to hold party-level resources (e.g., shared Luck pools). What it tracks and how it relates to its member actors is not yet understood well enough to design.

---

## Setting content lives in separate modules

Game-world content (setting lore, gear lists, factions, etc.) does not live in this repository. It belongs in separate Foundry modules generated by Artificer. The system provides the rules engine and sheet structure; modules provide the content that runs on top of it.

This separation means the system can be used with any 100DOS setting without bundling content it may not need, and it allows content to be updated independently of the system.

---

## Artificer generates content modules

[Artificer](https://github.com/AugmenTab/artificer) is a web service that generates Foundry content modules for the 100DOS system. It packages compendium packs, internationalization files, and (eventually) custom stylesheets. It does not inject content at runtime — it produces static Foundry module packages that are installed and loaded normally.

Artificer defers to this system on all structural and naming decisions. If there is tension between what Artificer needs and what the system needs, the system takes precedence and Artificer adapts.

---

## Error handling strategy: `Result<T, E>`

Calculations, formula evaluation, change application, and validation return a `Result<T, E>` discriminated union rather than throwing for expected failures. This keeps error paths explicit and composable without relying on try/catch.

```ts
type Result<T, E = string[]> =
  | { ok: true; value: T; warnings: string[] }
  | { ok: false; errors: E; warnings: string[] }
```

`warnings` is always present on both arms so callers never need to guard it. The default error type is `string[]`; the `E` parameter is available for structured errors where needed.

The helper module at `src/module/result.ts` exports:

- `ok(value, warnings?)` / `err(errors, warnings?)` — constructors
- `map(result, fn)` — transform a success value (fmap)
- `bind(result, fn)` — chain steps that can each fail; merges warnings (>>=)
- `traverse(items, fn)` — apply fn to each item in order, short-circuit on first failure
- `collect(results)` — fold over already-computed results, accumulate all errors

`traverse` and `collect` differ in error semantics: `traverse` stops at the first failure (suited for dependent pipeline steps), `collect` gathers every error (suited for independent validation).

No external functional programming library is used.

## Change data model

A change is a discrete modification applied to a derived stat during actor data preparation. Changes are stored on owned items; when an actor prepares its data it collects all changes from its embedded items and applies them.

Items that grant changes carry a `Changes` container with two arrays:

```ts
type Changes = {
  computed: ChangeData[];
  conditional: ConditionalChangeData[];
};
```

`ChangeData` represents changes the system applies automatically during actor data preparation:

```ts
type ChangeData = {
  id: string;          // stable identity for UI operations such as removal
  enabled: boolean;
  target: string;      // semantic path to the stat being modified
  mode: ChangeMode;    // "add" | "set"
  formula: string;     // value or roll expression
  source: ChangeSourceRef;
};
```

`ConditionalChangeData` represents changes that apply only under conditions the system cannot evaluate programmatically. These are descriptive rather than computed — shown to the player as a reminder rather than applied automatically.

```ts
type ConditionalChangeData = {
  id: string;
  enabled: boolean;
  target: string;
  value: string;  // freeform description, e.g. "+2 when attacking from elevation"
  source: ChangeSourceRef;
};

type ChangeSourceRef = {
  id: string;
  name: string;
};
```

The model carries no bonus type or stacking category. There is no Pathfinder-style distinction between bonus types; whether two changes of the same mode stack is determined by the target and application logic, not the change itself.

## Testing

The project uses three test tiers.

**Vitest** covers pure TypeScript modules — code with no Foundry dependency. Tests live alongside the modules they cover as `*.test.ts` files and run inside the dev container via `./scripts/test`. They are also run as part of `./scripts/build`, so they are enforced on every build. Any new pure-logic module must have a corresponding test file that covers all exported functions and their edge cases.

**Playwright browser tier** (`test/browser/`) covers 100DOS's own rendering: template output, markup structure, attributes, text, and CSS. Each test renders a real template from `src/templates/` through a local Handlebars instance with a hand-built context — no Foundry involved, so the tier runs in seconds. Fixture contexts are typed against the system's real data types and checked by `npm run typecheck:browser`, so a schema change surfaces as a type error rather than a stale render.

**Playwright e2e tier** (`test/e2e/`) covers behavior that needs Foundry's runtime: click handlers that open ApplicationV2 windows, form persistence and Document re-render, ProseMirror, and window lifecycle. It runs against a dedicated Foundry instance and world, separate from the development instance, and is the slow tier — new tests here should share setup where they can.

`scripts/ui-test` runs both Playwright tiers (the browser tier concurrently with Foundry startup); it is separate from `scripts/build`. See the README for running them, and `test/CLAUDE.md` for how to classify a new test into a tier.

**Rule:** whenever a new data type or utility module is added to `src/module/`, a test file must be added alongside it before the story is considered complete. The test must cover every field default (for data models) or every exported function (for utility modules).

## Character composition: Race, Soldier Type, Template

Sourcebooks build characters differently. Some (Mythic) let a Soldier Type
define the whole foundational profile. Others (Empires and Orders) take
the base Characteristics from a Race and add supplemental benefits from a
Soldier Type. One data model covers both, with no setting-specific code. The
planned single `archetype` Item type was dropped in favor of this model.

**Item types.** All three build on `AbstractItemData` (Changes, Actions,
child links, tags, identifier, `active`) and share `CompositionItemSheet`:

| Field | Template | Race | Soldier Type |
|---|---|---|---|
| `advances` (count 0–5 per Characteristic) | yes | yes | yes |
| `xpCost` | — | yes | yes |
| `baseCharacteristics` (all ten, explicit) | — | required | nullable |
| `baseMythicCharacteristics` (each nullable) | — | nullable | nullable |
| `baseSize` | — | required | nullable |
| `bodyLocations` (keyed `BodyLocation`s) | — | required | nullable |

Shared structures each live in their own module with a schema-field
constructor: `advances.ts`, `base-characteristics.ts`,
`base-mythic-characteristics.ts`, `size.ts`, and `body-location.ts`. Damage
Resistance composes `BodyLocation` with its per-Actor state (`destroyed`,
`value`, `contributions`).

**Absence is never zero.** A zero Characteristic is real (usually an injured
character), so `baseCharacteristics` is null until it is first authored, even
on a Race. The sheet won't save a partial lineup, and a Race's lineup can be
edited but never cleared. A Mythic value of `null` means the character
doesn't have it, which is different from `0`.

**Selection is activation.** An Actor may own any number of each type. At
most one Race and at most one Soldier Type are active, independently of each
other. Any number of Templates may be active. The Item's `system.active` is
the only record of the selection; there is no reference field on the Actor.
`Dos100Item` enforces the rule however an Item is activated (Dashboard
selector, Item sheet checkbox, acquisition, duplicate): the most recently
activated one wins, and its siblings are deactivated, so their child links
follow. The pure logic lives in `exclusive-activation.ts`.

**Acquisition.** Dropping a Race or Soldier Type from outside the Actor goes
through the same XP acquisition dialog as Abilities (Create / Skip /
Cancel), records to the XP ledger from the Item's `xpCost`, and creates the
Item active. Switching between owned Items is never an acquisition and never
charges XP.

**Future derivation contract** (not implemented). Foundational properties
resolve from the active Race first and fall back to the active Soldier Type.
Base Characteristics and Body Locations resolve as whole structures; Mythic
Characteristics resolve one value at a time, respecting null. Advances,
Changes and child Traits come from every active Race, Soldier Type and
Template. The Characteristic increase from Advances is
`5 * clamp(0, 5, sum of every source's count)`, without mutating the
sources. An Actor with no resolved Base Characteristics, Size or anatomy is
incomplete but may exist and be edited.

---

## Character creation wizard is post-MVP

No interactive character creation flow is planned during skeleton or initial sheet development. Characters are created by filling in sheet fields directly. A guided wizard may be added after the core sheet and data model are stable.
